# Infrastructure Tycoon

A PC-first Unity 2D management simulation about growing a single-PC hosting business into a cloud infrastructure provider.

## Development

Use **Unity 6.6 / 6000.6.9f1** (revision `8c45277fb9c5`), matching `ProjectSettings/ProjectVersion.txt`. This project deliberately uses the installed supported release rather than LTS.

Add this repository root in Unity Hub and open it with that editor. Allow Package Manager and asset import to finish. Commit Assets (including `.meta` files), Packages manifests and lockfile, and ProjectSettings; generated editor folders are ignored.

The foundation uses the built-in renderer, 2D editor defaults, Sprite tooling, uGUI, and Unity Test Framework. Open `Assets/Scenes/Main.unity` and enter Play Mode. The simulation starts on January 1, 1995 at 1x (two real seconds per day). Click PAUSE or 1x/2x/4x/8x to change the rate; the highlighted button and speed label show the selection. Pause preserves fractional-day progress, and selecting a running speed resumes the same session. Cash is live and updates after monthly billing; alerts remain a placeholder for a later phase. Run the Edit Mode simulation/catalog tests and Play Mode scene suite from Window > General > Test Runner. The same suite can run in a standalone Windows test player to verify real window resizing at 1280x720, 800x600, and 1920x1080; screenshots are saved under Application.temporaryCachePath.

The prototype garage uses reusable Garage, Player, and PCStation prefabs under Assets/Prefabs. Walk with WASD or arrow keys; diagonal movement is normalized and physics blockers stop the player at walls and the desk. Simulation pause leaves walking active. PCStation/Reach is a separate adjustable trigger from PCStation/Blocker; within reach, the [E] prompt appears and E opens the PC panel. Close it with CLOSE or Escape, or walk out of reach to close it automatically. The panel consumes repeated interaction and leaves the date/speed controls accessible; text input focus prevents E from opening a station behind the UI. The panel shows website offers, their resource requirements and monthly revenue, and accepted/hosted status. Click ACCEPT, then ASSIGN to put a website on the starter PC. Used/total CPU, RAM, storage, and bandwidth update immediately; the last completed month shows revenue, expenses, and net profit. Disabled controls and inline rejection messages explain unavailable actions. The camera fits the garage below the top HUD and above the status bar as the window resizes. World visuals are labeled prototype art, not a finished art pass.

Starter content is authored in `Assets/Data/StarterCatalog.asset`, referencing StarterPc, PhotoSnap, and LocalWebsite assets. Create definitions through Assets > Create > Infrastructure Tycoon. Keep explicit content IDs stable when renaming or moving assets. `StarterCatalog.ToRuntime()` validates references and IDs and creates immutable, engine-independent data; resource units are cores, GB, GB, and Mbps. Authored prices use whole dollars and convert to decimal runtime money. GameRoot references this catalog and creates an independent CompanySession with $150 cash, zero operating profit, one starter PC, and no accepted contracts. The session owns the existing clock; hardware runtime IDs are separate from content IDs. ResourceUsage exposes capacity, used demand, and available headroom in the same four units; available headroom clamps to zero for an overused dimension while retaining actual demand. CompanySession.TryAcceptOffer takes a stable offer content ID and returns a new runtime contract; TryAssignContract takes that contract ID and a hardware runtime ID. Both return a success flag and a UI-readable rejection reason. Accepted contracts start unassigned, while hosted contracts consume capacity. AvailableOffers excludes accepted offers. Acceptance and assignment do not change finances. At each outgoing month end, CompanySession bills full authored monthly revenue for hosted contracts and the PC expense once, updating cash and cumulative operating profit. Unassigned contracts earn nothing; there is no proration. BillingHistory and LastMonthlyResult expose the outgoing period, revenue, expenses, and net profit, while each hosted contract tracks PaidMonths. TryBillMonth rejects replayed or invalid periods. HostingPanel and the reusable HostingOfferRow prefab bind these session operations and read-only results to the PC panel.

Phase 3 content is authored in CpuUpgrade, RamUpgrade, StorageUpgrade, InternetUpgrade, and PhotoSnapGrowth assets under Assets/Data, referenced by StarterCatalog. Runtime catalog Upgrades and Milestones are immutable snapshots with globally unique content IDs and validated hardware/offer targets. Upgrade prices/deltas are provisionally $120/+2 cores, $80/+4 GB RAM, $100/+250 GB storage, and $90/+10 Mbps. PhotoSnap growth targets two paid months and a 2-core workload; its other requirements and $100 revenue stay unchanged. Definitions remain separate from session state; purchase operations and automatic milestone application follow in the Phase 3 task queue.

HardwareInstance exposes BaseCapacity, EffectiveCapacity, PurchaseRecords, and AppliedUpgradeIds; each immutable UpgradePurchase records hardware runtime ID, upgrade content ID, and the historical amount paid. ContractInstance exposes BaseRequirements, EffectiveRequirements, and AppliedMilestoneIds. Explicit state constructors copy and validate their inputs without charging money or changing another session. ProgressionResources calculates capacity from additive upgrade deltas, selects the latest explicitly applied workload profile by paid-month threshold, and calculates assigned demand/headroom. It retains overload demand above capacity while available headroom clamps to zero. Calculated usage is a returned snapshot; session code owns committing resource state. Fresh live sessions still have no purchases or automatically applied milestones. Version 2 persistence supports these explicit states; version 1 migration activates eligible legacy milestones without replaying payments.

Session save serialization is available through SessionSaveJson.Capture(session, gameVersion), ToJson(snapshot), and TryLoad(json, catalog, out restoredSession, out reason). Capture between session updates; capture during a clock boundary callback is rejected. Version 2 preserves the required metadata, decimal finances, fractional-day progress, selected speed, runtime/content IDs, assignments, paid-month counts, and complete billing ledger. Each hardware entry also requires a purchases array (records carry hardware runtime ID, upgrade content ID, and historical amount paid); each contract requires applied_milestone_ids. Applied upgrade IDs are derived from the purchase records. Empty arrays are required when no progression is applied. Capacities and demand are rebuilt from the supplied catalog. Loading validates a separate session before the UI replaces live state. The format still describes one starter PC; recorded upgrade spending reduces cash without reducing operating profit. Valid historical growth overloads are restored, while new assignments retain capacity checks. Version 1 files migrate in memory with no purchases and eligible PhotoSnap growth based on saved paid-month counts. Unsupported future versions and inconsistent progression are rejected. Loading does not rewrite the file; the next explicit SAVE writes version 2 to the same historical filename. Use SAVE and LOAD in the HUD from anywhere in the garage. The single slot is `company-v1.json` under `Application.persistentDataPath`. Saves run after the frame simulation update, flush a temporary sibling file, and atomically replace the previous slot; failures preserve the previous file. Loading closes the PC panel and refreshes the clock/cash HUD; reopening the panel rebuilds its controls for the restored company. Player position, station triggers, and panel-open state are not saved. Missing, invalid, unsupported, or inaccessible saves show a short HUD message and leave the current company active. Tests inject unique temporary slots through GameRoot.ConfigureSaveSlot and clean up only those files.

## Phase 2 verified playthrough

1. Open Main in Play Mode for a fresh $150 company. Walk to the PC using WASD/arrows; E stays inactive out of reach and opens the panel within reach.
2. ACCEPT PhotoSnap, then ASSIGN it. Usage becomes 1/2 CPU cores, 2/4 GB RAM, 20/250 GB storage, and 4/10 Mbps. Acceptance alone consumes no resources.
3. Pause on January 31, SAVE, then LOAD. The company, assignment, selected speed, and partial day resume; loading closes the panel. Reopen it with E if still within reach.
4. Resume across February 1. January's result is $100 revenue, $20 expense, and $80 net, leaving $230 cash. SAVE after that payment and LOAD repeatedly: the payment must not repeat.
5. Resume across March 1. February pays once, leaving $310 cash and two paid months for PhotoSnap. Pause and speed controls continue to affect the restored company.

Verified on November 13, 2026 with Unity 6000.6.9f1:

| Suite | Passed |

| Edit Mode | 86/86 |
| Editor Play Mode | 20/20 |
| Standalone Windows Play Mode | 20/20 |

`Phase2LoopTests.FreshGameWalkHostSaveBeforeAndAfterBillingThenResumeNextMonth` covers this complete sequence. It drives the keyboard's physics movement motor without teleporting, routes interaction through the E-key handler, and uses UI pointer events (including real raycast checks in the standalone player). Calendar advancement is accelerated deterministically through the clock API; the pre-rollover snapshot preserves exactly 0.75 day progress. Other suites cover every speed's real frame advancement, collisions, reach/re-entry, rejection paths, malformed saves, and failed file replacement.

Run all Edit Mode and Play Mode suites in Window > General > Test Runner. For the standalone check, run the installed Unity editor with `-batchmode -projectPath <repo-root> -runTests -testPlatform StandaloneWindows64 -testResults <results.xml> -logFile <editor.log>`. The integrated test saves `Phase2-Resumed-800x600.png` and `Phase2-Resumed-1280x720.png` under `Application.temporaryCachePath`; both layouts were visually inspected. Tests use unique temporary save directories and clean their slots without touching the player's save.

The garage, player, and PC remain labeled prototype art. Capacity upgrades, PhotoSnap growth, bottleneck alerts, and later progression are outside this verified Phase 2 milestone.
